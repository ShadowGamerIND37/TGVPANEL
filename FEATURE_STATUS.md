## Roadmap phase status (Phase 0 baseline)

The **only roadmap system classified FULLY IMPLEMENTED is the existing reseller system**, as directed by the owner. Other areas may contain implemented/tested slices, but remain partial or not implemented at phase scope.

| 1 — VPS management | PARTIALLY IMPLEMENTED (in progress) | Existing KVM/LXC lifecycle, reinstall, serial/SSH consoles and selected configuration remain. Additive v019 task history and async lifecycle support now provide per-instance exclusion for unified lifecycle calls, authorized status/history APIs and UI polling. Existing per-instance KVM mutation routes in `app.js` and all direct `/api/v1/lxc/:id` mutation routes share task lock/history; reseller VPS lifecycle calls use the same manager lock/history without changing their synchronous contract. New per-instance mutation routes must adopt this path. A KVM `shutdown` action distinct from `stop` is implemented (SIGTERM with a longer grace period and no forced kill, exposed through the unified action API, the legacy `/api/vms/:vm_id/shutdown` route, and the KVM detail UI); LXC rejects `shutdown` because containers have no graceful guest shutdown. Workers are in-process, not a distributed queue. On controller startup, unfinished tasks are marked interrupted rather than silently retried. KVM virtual-disk expansion is now supported offline for standalone QCOW2/raw images; guest filesystem growth remains an in-guest step. KVM clone is limited to stopped user-mode NAT VMs and only clones the standalone primary disk; guest identity/security artifacts remain duplicated until regenerated. LXC clone now uses `lxc-copy` for stopped directory-backed containers only; it remains stopped and host-network-detached, and the guest identity/secrets/static network config remain copied. Real `lxc-copy` host interoperability is not tested here. Clone rollback is implemented and verified by failure-injection tests: a failed KVM clone removes the created disk image and inserted VM/registry rows, and a failed LXC clone destroys the created host container and removes the inserted rows (T08). Migration v022 adds a non-suspending staff service lock for KVM/LXC; it blocks starts/restarts but deliberately does not stop already-running guests. KVM also has a guided operator-supplied rescue ISO boot/restore flow, with no bundled or validated rescue media. KVM VNC/noVNC is available through a local-only QEMU VNC port and authenticated WebSocket proxy. Automated guest repair/LXC rescue remain unsupported. ## Reseller API key slice (verified)

- Credentials: random `tgvpk_…` key ID and 256-bit secret; key and secret hashes plus AES-256-GCM-encrypted HMAC secret at rest. The pair is returned only at create/rotate.
- Request protection: documented HMAC-SHA256 canonicalization, five-minute timestamp tolerance, durable one-use nonce records, exact IP allowlists, per-key requests/minute, and request outcome logs.
- Scope model: permissions come from an allowlisted catalog; current endpoints enforce granular scopes and owner checks. Generic API keys and node-agent signatures remain separate and backward-compatible.
- Administration: reseller owner can list/update/disable/enable/revoke/rotate their own keys; admin can inspect key metadata, disable, or revoke without seeing a secret. Admin can list reseller accounts with real owned-VPS resource totals and suspend/unsuspend accounts; suspension disables keys and unsuspension does not silently re-enable them.
- Actual data APIs: reseller VPS read/list (owner-only, paginated and filterable), start/stop/restart, stats, aggregate resources, and per-VPS resource usage delegate to existing database and virtualization managers. Customer CRUD manages isolated CRM records only; there is no linked customer login, customer-VPS relationship, or reseller provisioning. Quotas, plans, billing, and reserved scopes remain unavailable until their backing services are implemented.
- Verification: `npm run build`, `npm test` (**34/34**), including T33 HMAC, tamper, replay, authorization, rotation, IP/rate, audit and owner-isolation checks; T34 exercises lifecycle task concurrency and access controls.
