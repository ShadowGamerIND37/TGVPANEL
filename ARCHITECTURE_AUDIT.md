# TGVPANEL Architecture Audit

**Audit baseline:** active branch `arena/1339f942-tgvpanel`, based on `97e5d76c41f10ebbd0066230fb4917d14e27c6df` (`main`, merge of PR #40). Audited against the complete Virtualizor-level upgrade roadmap (sections A–R). Audit-only pass: no production functionality was modified.

## Product and runtime

- **Repository/product:** `ShadowGamerIND37/TGVPANEL`; existing product, TGVPANEL branding. This change must preserve it and extend in place.
- **Process:** root `app.js` is the existing Express 4 / `http.Server` entry point, legacy KVM integration and static/EJS server. It initializes the TypeScript runtime compiled into `lib/`, attaches session/CSRF/auth middleware and mounts `/api/v1` and unified web routes. Do not replace the root runtime.
- **Application code:** `src/` is TypeScript and compiles to checked-in runtime `lib/` via `npm run build` (`tsconfig.json`). Frontend remains EJS plus browser JavaScript/CSS in `views/` and `public/`; do not rewrite it.
- **Persistence:** SQLite (`src/db/database.ts`, `src/db/migrations.ts`, `data/tgvpanel.db`) with ordered, checksummed migrations and pre-migration backup behavior. `docs/POSTGRESQL_MIGRATION.md` is a migration plan, not evidence of PostgreSQL runtime support. Keep production/user DBs untouched in tests; the suite clones the DB to temp storage.
- **Node agents:** `src/node-agent/` implements an independent Node HTTP agent, allowlisted command execution, container/console/snapshot/transfer facilities, signed communication and health. `src/services/nodes/NodeClient.ts` owns controller pairing, HTTPS/TLS pinning, remote requests and node lifecycle.

## Existing request/data flow

1. `app.js` parses JSON and retains raw request bytes, establishes the session, applies CSRF/security checks and sets a unified principal through compiled TypeScript middleware.
2. `/api/v1` routes use `HkvmRuntimeContext` and delegate to services; instance access checks use `InstanceManager.getAuthorizedInstance` and role/owner/shared state.
3. Adapters perform virtualization operations; remote compute operations pass through `NodeClient` to a Node Agent using signed requests/TLS checks. Agent commands use allowlists and path validation.
4. Service state is stored in the SQLite database through versioned migrations; timers currently run in-process, with limited domain-specific task state.
5. Existing EJS pages call same-origin JSON endpoints. The changes retain that model.

## Observed security and compatibility constraints

- `normalizeRole` originally recognized only admin/subadmin/operator/user/readonly; role additions must be explicit and avoid treating reseller as staff.
- `InstanceManager.isStaff` deliberately excludes normal users; resellers must remain non-staff and their API listing must filter to records they own, not shared instances or other tenants.
- Generic `api_keys` are SHA-256 hashed bearer tokens with coarse read/write/admin permissions. Do not retrofit HMAC storage in a way that invalidates existing keys.
- Session mutations require CSRF. Machine-signed reseller calls need a dedicated signature verification path before generic principal enforcement and must not weaken browser CSRF checks.
- `createRateLimiter()` in `src/security/middleware.ts` trusts the first `X-Forwarded-For` value; no Express `trust proxy` configuration was found in `app.js`. `app.js` configures session cookies with `secure: false`. These require deployment-aware review (trusted proxy configuration and secure cookies on HTTPS) and spoofing/session transport regression tests; no functional change was made during the audit.
- HMAC secrets need verification material: store a hash and an encrypted copy under the existing AES-GCM vault, show raw values once, never put secrets in logs/admin views, and use durable unique nonce records to prevent replay across process restarts.
- Rate limits and IP allowlists must be keyed to individual reseller keys. Admin inspection must expose metadata only; disable/revoke must take effect immediately.
- Additive SQLite migrations and existing row preservation are mandatory. Do not change engine support claims or replace working operations with fakes.

## Architecture findings and consequences

- TGVPANEL is a KVM/LXC platform with optional multi-node agent communication, not a generic Virtualizor-compatible adapter framework yet.
- Migration v018 adds a reseller-owned CRM contact registry with strict owner filtering and direct deletion; it intentionally does not link contacts to TGVPANEL users or VPS records. There is still no customer/VPS ownership graph, reseller quota ledger, plans, invoices, verified payment integration or billing model. Current user-owned VPS records are not a substitute for reseller customer isolation.
- The existing reseller account/key/API management contract is implemented and verified: reseller role and oversight, isolated HMAC key/secret lifecycle, signed owner-scoped paginated/filterable VPS listing and read/start/stop/restart, stats/resources, durable nonces, per-key permissions/IP/rates/logs, admin account suspension with key disablement, reseller/admin pages, and additive SQLite migrations v017–v018. Treat this as a completed existing subsystem and preserve compatibility; `FEATURE_STATUS.md` and `docs/API_RESELLER.md` record the shipped contract and signing bytes.
- CRM customer CRUD is a reseller-owned contact directory; it does not create customer logins or confer VPS access. Billing, customer-VPS assignment, resource quotas/allocation, plans, IP guarantees, and invoices/payment verification are distinct unimplemented extensions, not reasons to rebuild or replace reseller management.
- KVM telemetry fidelity: Phase 0 found `KVMAdapter.getTelemetry()` returning constant-zero network RX/TX and `mapRowToUnified()` substituting `127.0.0.1` for a missing IP. Phase 1 changed those unavailable fields to null; KVM network traffic is still not measured. KVM CPU/RAM remain host-process `/proc` observations and disk-used is the disk-image file size, not guest-level metrics. LXC/node metrics have separate real host/cgroup collection paths, with coverage limits recorded in `FEATURE_GAP_ANALYSIS.md`.
- Controller timer loops cannot provide distributed job locking or cluster HA guarantees. Keep those gaps visible and do not claim safe failover.

## Phase 1 implementation progress (not complete)

- v019 adds `instance_tasks` with status, optional measured progress, step text, result/error and timestamps; a partial unique index serializes queued/running unified lifecycle operations per VPS. `InstanceTaskManager` persists records and marks all unfinished work from the previous controller process interrupted at startup instead of retrying it blindly.
- Unified `/api/v1/instances` lifecycle calls remain synchronous by default and record task history; supplying `async: true` returns HTTP 202 with a task ID. Unified bulk lifecycle operations also use the lock/history path. Legacy KVM lifecycle/delete and selected mutation routes in `app.js` (start/stop/restart/delete, reinstall, ISO attach/detach, snapshot create, configuration edit, and guest serial-console commands) share the lock/history while retaining synchronous response contracts. All direct `/api/v1/lxc/:id` mutation routes (resize/reinstall/network repair/password/SSH key/tunnel/renew/ownership/sharing/file write/delete) use task locking/history; LXC provisioning retains its own install state. Some non-lifecycle legacy mutations remain outside task history. Reseller lifecycle calls now pass through the same synchronous tracked `InstanceManager.executeAction` path; their URL/authentication/key schema, request and response contracts remain unchanged. Other reseller key/customer/account endpoints do not target VPS lifecycle and are not VPS instance tasks.
- KVM disk size changes through the legacy edit form and `/api/v1/instances/kvm/:id/disk/resize` perform a real, stopped-VM expansion for managed standalone QCOW2/raw images. Shrink, backing-chain images and paths outside the managed VM directory are rejected. The operation does not resize the guest partition/filesystem; that remains a guest-side step. The admin license copy now names supported console paths; KVM VNC is configured stopped-only, listens on loopback, and is proxied through the authenticated noVNC page/WebSocket.
- Lifecycle and direct mutation adapters report stage text but not measured percentages; UI progress remains indeterminate rather than fabricated. Legacy middleware retains its lock after client disconnect because hypervisor work is not cancellable. A hung route can leave an active task until stale-task recovery/restart; workers are in-process and not distributed.
- All current direct `/api/v1/lxc/:id` mutation routes use the task lock/history helper (T34 verifies conflicts for password and file-write paths). All enumerated existing per-instance legacy KVM mutations use the same lock/history middleware, including start/stop/restart/delete, configuration/reinstall, ISO, snapshots, and serial-console commands. Reseller VPS lifecycle calls use the manager task lock/history and keep the same synchronous HTTP contract; unrelated reseller keys/customer/account APIs remain untouched.
- KVM disk expansion and secondary-device APIs are tested through an injected command runner. Production disk resize/add needs `qemu-img`, a stopped VM, and managed images. Additional disk/NIC changes are offline only; disk detach preserves its image for reattach, and secondary NICs are user-mode NAT only. Guest filesystem growth remains in-guest. Real-hypervisor execution was not available in this sandbox.
- Implemented in this pass: stopped-NAT KVM primary-disk clone (with duplicated guest identity/secrets disclosed), stopped directory-backed LXC clone through allowlisted native `lxc-copy` (clone remains stopped with host networking removed), offline KVM secondary QCOW2 disk and user-mode NAT NIC workflows, and stopped-only loopback QEMU VNC with an authenticated browser noVNC proxy. LXC guest identity/secrets and in-guest static network settings remain copied and require operator review; only the adapter/API path is tested with a stub, not real host `lxc-copy` interoperability. The VNC page and binary WebSocket-to-TCP proxy enforce login and per-VM owner/shared/staff authorization; the upstream address is fixed to `127.0.0.1` and the TCP port is loaded from the authorized VM row rather than client input. VNC and device controls are unavailable for LXC. The proxy integration is socket-tested; real QEMU/noVNC protocol interoperability remains unverified.
- Phase 1 remains in progress; Phase 2 must not start until its supported scope and integration gates are closed. Remaining limits: LXC clone only supports stopped directory-backed containers; LXC clone and KVM VNC have stub/socket tests but no real-host interoperability; KVM rescue only selects operator-supplied ISO media and does not reset passwords or repair filesystems; there is no bundled/validated rescue image or automated guest recovery. Task workers run in-process and mark unfinished work interrupted on restart; measured percentages remain indeterminate unless an adapter can report real progress. A general distributed queue is a later roadmap concern, not represented as implemented here. Migration v022 supplies a staff-only non-suspending lock that blocks start/restart without stopping an already-running guest. Do not expose unsupported controls or represent these limitations as complete.

Real QEMU interoperability was not validated.
