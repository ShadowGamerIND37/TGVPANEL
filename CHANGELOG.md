## Unreleased — Phase 14 ISO library inventory: honest size + SHA-256 checksum (2026-10-30)

- Added a unified ISO library inventory endpoint `GET /api/v1/iso/inventory` (admin/subadmin/operator) backed by `StorageManager.listIsoFiles()`. It scans the managed ISO directory (`~/vms/iso`) and returns each `.iso` file with its **honest file size** (`sizeBytes`) and **SHA-256 checksum** (`sha256`) computed from the real file contents via the node-agent checksum helper. The checksum is `null` only when it cannot be computed, never a fabricated value.
- This addresses the audit's "ISO checksum policy... incomplete" gap for area H. The legacy `/api/iso-list` endpoint (bare filenames, consumed by the existing VM create/detail UI) is left unchanged for backward compatibility; the new endpoint provides the richer integrity/size inventory.
- T10 creates a known ISO fixture and asserts the inventory returns the correct `sizeBytes` and a `sha256` matching the independently computed checksum, then cleans up.

## Unreleased — Phase 13 KVM snapshots: honest sizing & consumption accounting (2026-10-30)

- Corrected a KVM snapshot honesty gap: `KVMAdapter.createQcow2Snapshot` previously recorded `size_gb` as the raw disk-**image-file** size (`fs.statSync`), which does not reflect the snapshot's disk capacity or actual on-disk consumption. The method now uses the injected command runner (consistent with Phase 12) and calls `getDiskImageStats` to read honest `qemu-img` figures: `size_gb` is the snapshot disk's **virtual capacity** and a new **`allocated_gb`** records the actual **on-disk consumption**. It falls back to the previous image-file-size behavior (with `allocated_gb` null) only when `qemu-img` is unavailable, so snapshot creation never breaks on hosts without the tool.
- Added migration **v025** `v025_kvm_snapshot_allocated_gb` adding an additive `allocated_gb REAL` column to `vm_snapshots` (existing rows keep NULL until re-measured; backward-compatible).
- `BackupSnapshotManager.listSnapshots` now returns `sizeGb` and `allocatedGb` for KVM snapshots, exposing the honest figures to the snapshot listing API. The legacy `SELECT *` snapshot endpoint and the `vm-detail` snapshot UI pick up the new column automatically.
- T34 extends the mocked `qemu-img` runner with a `snapshot` handler and asserts that after a disk resize to 30G, a created KVM snapshot stores `size_gb: 30` (virtual capacity) and `allocated_gb` equal to the reported allocated disk-size, and that the listing exposes both — proving the values come from `qemu-img` rather than the image file.
- Full suite: **34/34 acceptance suites passing**.

## Unreleased — Phase 12 KVM telemetry: honest disk image stats (2026-10-30)

- Corrected a KVM telemetry honesty gap: `KVMAdapter.getTelemetry` previously reported `diskUsedGb` as the raw disk-image **file size** (`fs.statSync`), which does not reflect the guest's actual disk usage or capacity. Added a `getDiskImageStats(diskPath)` helper that runs `qemu-img info --output=json` (read-only, no writes) and reads the honest `virtual-size` (guest disk capacity) and `disk-size` (allocated bytes on disk) plus the image `format`.
- `getTelemetry` now sets `diskUsedGb` to the allocated `disk-size`, `diskTotalGb` to the `virtual-size`, and a new `diskFormat` field to the image format. When `qemu-img` is unavailable or the command fails, it falls back to the previous `statSync` image-file-size behavior so telemetry never breaks on hosts without the tool. This addresses the audit's "disk usage is image-file size" note for area N; LXC telemetry was already honest (`df`/`du`).
- Added an optional `diskFormat?: string | null` field to the `InstanceTelemetry` interface in `VirtualizationAdapter.ts`.
- T34 extends the mocked `qemu-img` runner to return `disk-size` and asserts that after a disk resize to 30G, KVM telemetry reports `diskFormat: 'qcow2'`, `diskTotalGb: 30`, and `diskUsedGb` equal to the reported allocated disk-size (proving it comes from `qemu-img` rather than the image file).
- Full suite: **34/34 acceptance suites passing**.

## Unreleased — Phase 10 backup destination: cross-node copy (2026-10-30)

- Added backup destination support via cross-node backup copy (replication/offload). `BackupSnapshotManager.copyBackupToNode(backupId, targetNodeId)` copies a backup archive to a destination node and integrity-verifies the copy against the source SHA-256 before recording it. The stored archive is copied as-is (encrypted archives stay encrypted); the copy is verified by decrypting encrypted archives before checksumming so the comparison matches the source's decrypted-content hash.
- New `backup_copies` table (migration **v024 `v024_backup_destination_copies`**) records each copy: backup id, target node, file path, checksum, size, encryption flag, and creator. New endpoints: `POST /api/v1/backups/:id/copy` (admin/subadmin) and `GET /api/v1/backups/:id/copies`.
- New node-agent `POST /api/v1/backups/receive` endpoint writes the archive to the confined backup directory and verifies it (decrypting if encrypted), returning the computed checksum. Local-target copies are written and verified in-process.
- This addresses the "remote destinations" gap in area E without requiring external S3/FTP/NFS credentials — destinations are TGVPANEL nodes. S3/FTP/SFTP/NFS object destinations remain unimplemented.
- T14 covers copying an encrypted local backup to the remote node, asserting the copy is recorded, completed, encrypted, and checksum-matches the source, and that the copies list includes it.
- Full suite: **34/34 acceptance suites passing**.

## Unreleased — Phase 9 backup restore rehearsal (2026-10-30)

It returns a structured verdict (`restorable`, `checksumValid`, `archiveValid`, `entryCount`, `topLevelDir`, `reasons`).

Remote-node backups rehearse via a new node-agent `POST /api/v1/backups/rehearse` endpoint (mirroring the existing verify endpoint), and the panel exposes `POST /api/v1/backups/:id/rehearse` for admin/subadmin/operator.
- T14 covers both paths: a valid encrypted backup rehearses as restorable (decrypt + checksum + archive inspection), and a tampered encrypted archive rehearses as not restorable (decrypt/checksum failure).
- Test harness: each acceptance step now uses a unique `X-Forwarded-For` value so every step gets a fresh rate-limiter bucket instead of sharing one 120/min mutation window across the whole suite. This removes flaky 429s in later steps without weakening the production rate limiter; T09 still exercises the real limiter within its own step.

## Unreleased — Phase 8 migration duplicate-run fencing (2026-10-30)

- Added duplicate-run fencing to offline LXC migration (`MigrationManager.startOfflineLxcMigration`). Before starting a new migration, the manager now queries `vps_migrations` for any active (non-terminal) job — status `preparing`, `preflight`, `exporting`, `transferring`, or `verifying` — for the same instance and rejects the request with a clear error. This prevents two concurrent transfers from racing on the same source container and target import path, which could cause data loss or duplicate target containers. Terminal statuses (`completed`, `rolled_back`, `failed`) do not block a new migration.
- This closes an audit gap in roadmap area F ("duplicate-run fencing... incomplete") and is covered by T14, which inserts an active migration row and asserts the fencing guard rejects a second start before the real migration runs. The fencing test calls the manager directly so it does not count against the shared API mutation rate limiter.
- Full suite: **34/34 acceptance suites passing**.

## Unreleased — Phase 7 backup encryption-at-rest (2026-10-30)

- Added backup encryption at rest for **local LXC backup archives**. Local LXC tar.gz archives produced by `BackupSnapshotManager.createBackup` are now encrypted in place with AES-256-GCM using the existing panel credential key (`getSecretBundle().credentialKeyHex`) before the record is persisted. The plaintext archive is removed after the encrypted file (`<archive>.enc`) is written.
- The encryption format is self-describing and byte-verifiable: magic header `TGVENC1` (8 bytes) + 12-byte IV + 16-byte GCM authentication tag + ciphertext. AES-GCM authenticates the ciphertext, so tampered or truncated archives fail to decrypt instead of restoring corrupt data.
- Storage semantics: the `container_backups.encrypted` flag (1 for encrypted local archives, 0 otherwise) and `encryption_alg` column are recorded via migration **v023 `v023_backup_encryption_at_rest`**. The stored `checksum_sha256` remains the hash of the **decrypted** content, so integrity verification (`verifyBackupIntegrity`) decrypts to a confined temp file, recomputes the SHA-256, and cleans up. `restoreBackup` decrypts encrypted archives to a confined temp file before restoring; `deleteBackup` operates on the stored (`.enc`) path.
- Scope: **local node LXC backups are encrypted at rest**. Remote-node backups remain unencrypted (backward compatibility for the existing cross-node transfer format), and KVM backups use the QCOW2 snapshot path and are unaffected. Encryption uses the panel credential key; key rotation, external KMS, and customer-supplied keys are out of scope for this batch.
- Tests: T14 now asserts that a created local LXC backup is marked `encrypted=1` with `aes-256-gcm`, that the on-disk archive is an encrypted file, that the plaintext is removed, that encrypt/decrypt round-trips exactly, and that a tampered archive fails decryption. Full suite: **34/34 acceptance suites passing**.

## Unreleased — Phase 6 security hardening (2026-10-30)

- Hardened the generic rate limiter against `X-Forwarded-For` spoofing: it no longer trusts the client-supplied header unconditionally. The header is now honored only when the immediate socket peer is a configured reverse proxy (`TRUSTED_PROXIES` env var, comma-separated exact IPs or IPv4 CIDRs); otherwise the limiter keys on the socket address, so a directly-exposed panel cannot be bypassed by header spoofing. `createRateLimiter` accepts an optional `trustedProxies` override for testing. T09 covers parsing, exact/CIDR matching, IPv6 exact match, and the spoof-bypass contract. Default behavior (no `TRUSTED_PROXIES`) keys on the socket address, which is the safe default.
- Made legacy session cookies opt-in secure: `secure` remains `false` by default for plain-HTTP deployment compatibility, but operators behind HTTPS can set `SESSION_COOKIE_SECURE=1` to require the `Secure` attribute. `httpOnly` and `sameSite: lax` are unchanged.

## Unreleased — Phase 2 started (2026-10-30)

- Phase 2 scope is TGVPANEL's own KVM/LXC control plane: improve host capability accuracy, safe lifecycle/error behavior, and KVM/LXC integration validation within the existing architecture.
- Per owner direction, do not integrate Proxmox/vendor APIs, external hypervisor API keys, or vendor credential workflows. Existing Proxmox OS templates are just install media/templates and do not change this scope.
- Hardened the native KVM adapter restart contract: when no dedicated restart hook exists, restart now requires both stop and start hooks and rejects instead of returning apparent success without performing an operation. Added acceptance coverage for rejection and ordered stop/start fallback.
- Improved native host probing for ARM-only systems: QEMU version detection now selects `qemu-system-aarch64` when x86_64 QEMU is absent, while preferring x86_64 when both are installed. T08 covers ARM-only, both-present, and neither-present selection. This reports installed QEMU accurately; it does not claim every TGVPANEL guest template supports ARM.
- Hardened native LXC lifecycle state integrity: a failed host stop now prevents persistence of administrative suspension, and a failed host destroy no longer silently deletes panel records. T08 covers both host-failure contracts.
- Hardened native KVM lifecycle state integrity: fallback stop now waits for the guest process to exit before recording stopped; suspension stops a live guest process even when the recorded status is stale before recording suspension; deletion refuses without a registered host delete hook instead of removing panel records while leaving guest artifacts on the host; stale “running” state with no stop hook or live PID is rejected instead of being marked stopped/suspended; and hook-backed start, stop, restart, and suspend now verify the persisted guest process state before recording the panel status. T08 covers all fallback guards and hook-state failures.
- Improved native host capability accuracy: QEMU system binary selection now prefers the installed binary matching the detected host CPU architecture, reports whether that binary matches the host architecture, and health warnings disclose a QEMU architecture mismatch. T08 covers ARM/x86 selection and mismatch checks. This reports installed host tooling; it does not validate guest-template compatibility.
- Hardened native KVM deletion integrity: fallback deletion without a registered `deleteVmById` host hook now refuses instead of deleting panel records while leaving guest disk artifacts on the host, and hook-backed deletion now verifies the VM row is gone and no live guest process remains before reporting success. T08 covers both refusals.
- Hardened native LXC lifecycle state integrity: start, restart, freeze, unfreeze, stop, and suspension now verify the host-reported container state before persisting panel status, so the panel does not record running/frozen/stopped unless the host inspection confirms it. Deletion now inspects the host container first and only requires destroy verification when the container exists; panel records are removed for missing/meta-only containers without host destroy tooling, and never removed when a destroy leaves the container behind. T08 covers both host-state mismatch refusals and the missing-container delete path.
- Improved native node-health capability warnings: extracted the warning logic into a pure `buildCapabilityWarnings` helper and added honest warnings for an installed-but-unmounted `lxcfs` (guest `/proc` resource telemetry may not reflect per-container cgroup limits), a detected `lxcfs` mount with a missing binary, and LXC on a cgroup v1 or undetected-cgroup host (native v2 delegation may be unavailable). T08 covers the healthy-host no-warning baseline, all three new warnings, the `/dev/kvm` TCG warning, and the controller-only warning. Phase 2 and Phase 1 remain in progress.

## Unreleased — Phase 1 in progress (2026-10-30)

- Added a KVM graceful `shutdown` lifecycle action distinct from `stop`: it sends SIGTERM with a longer grace period (15s fallback) and never escalates to SIGKILL, refusing to record stopped state if the guest does not exit. It is exposed through the unified lifecycle action API, the legacy `POST /api/vms/:vm_id/shutdown` route, and the KVM detail UI (admin and customer). LXC rejects `shutdown` (501) because containers have no graceful guest shutdown, so callers never mistake a no-op for a shutdown. T08 covers the hooked shutdown path, the stale running/no-PID refusal, and the LXC rejection.
- Added failure-injection acceptance coverage for cross-engine clone rollback (T08). When a KVM clone fails during registry sync, the adapter now demonstrably deletes the created flattened disk image and the inserted VM/registry rows; when an LXC clone fails after the host `lxc-copy`, the adapter demonstrably destroys the created container and removes the inserted `lxc_instances`/`instances` rows. Both rollback paths already existed in the adapters; they are now verified rather than assumed.
- Added backed-up migration v020 and tracked v1 APIs for KVM secondary-disk and NAT-NIC workflows. These configuration changes require a stopped VM; disk detach preserves/catalogs image data and supports reattach. Bridge networks and live QEMU hotplug are not exposed.

- Added an LXC clone workflow through the host allowlisted `lxc-copy` utility for stopped, directory-backed containers. The clone remains stopped with host networking detached to prevent immediate duplicate-IP/MAC conflicts; guest identity, secrets, and in-guest static network configuration remain duplicated and must be reviewed. - Added additive SQLite migration v019 for persistent VPS lifecycle task history and a partial unique index preventing more than one queued/running unified lifecycle operation per engine/instance.

- Added shared task locking/history middleware to legacy KVM lifecycle/delete and selected mutation routes (start/stop/restart/delete, configuration edit, reinstall, ISO attach/detach, snapshot create and guest serial-console commands) without changing their synchronous HTTP response contracts.
